## 执行摘要

小安已确认：完整自研内核 + 全应用兼容 = 航母级工程，小团队负 ROI。

**本方案的立场**：不造内核，走 **Linux 定制 + Wine 兼容层** 路线，在合理周期内交付可用的跨平台桌面操作系统。目标是在 Phase 1 让 Linux 桌面开箱即用（无需用户折腾），Phase 2 建立应用认证商店，Phase 3 对 macOS 兼容性给出明确结论。

## 一、技术架构

### 1.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                   用户应用层                              │
│   Windows 应用（.exe/.msi）│ Linux 应用（deb/rpm）       │
│   │ via Wine 兼容层         │ 直接运行                   │
├────────────────┬──────────────────────────────┬─────────┤
│   Wine 兼容层    │  桌面环境 / Shell (Cinnamon) │  WebApp │
│  （Win32→POSIX） │   （Ubuntu 定制）             │  Runtime│
├────────────────┴──────────┬─────────────────────┴─────────┤
│     系统服务层             │     应用生态层               │
│  • Display Manager        │  • App Store (Phase 2)       │
│  • 软件包管理器（APT）      │  • Wine 应用认证体系          │
│  • 网络/蓝牙/电源管理       │  • 一键安装脚本               │
├───────────────────────────┴────────────────────────────┤
│              Ubuntu 24.04 LTS 定制内核                    │
│         （预装驱动 + Wine + 开箱即用配置）                │
├─────────────────────────────────────────────────────────┤
│              硬件抽象层（物理机 / 虚拟机）                  │
└─────────────────────────────────────────────────────────┘
```

### 1.2 核心模块依赖关系

```
硬件层
  ↑
Ubuntu 定制内核层（预编译驱动、默认固件）
  ↑
系统服务层（display-manager, network-manager, udev, pulseaudio）
  ↑
桌面环境（Cinnamon，兼顾美观 + 低资源占用）
  ↑
Wine 兼容层（核心差异化模块）
  ↑
Wine 应用认证商店（Phase 2 新增）
  ↑
用户直接使用层
```

### 1.3 数据流

```
用户双击 .exe
  → GNOME/MATE 文件管理器（Nautilus/Caja）
    → MIME 类型识别（.exe → wine-launcher）
      → Wine 运行时启动
        → Wine DLL 翻译层（ntoskrnl.exe替代 + Win32 API翻译）
          → Ubuntu 系统调用（POSIX / Linux kernel）
            → 硬件执行
```

```
用户 apt install <应用>
  → APT 包管理器
    → 项目维护的自定义 deb 仓库（Private PPA / 独立 repo）
      → 预验证依赖 + Wine 包装器脚本
        → 一键安装，无需命令行
```

## 二、Phase 1 详细计划（Week 0–12）

**目标**：产出可用 Alpha，Ubuntu 定制发行版，可开箱运行主流 Windows 软件，无需用户干预。

### Week 1–2：基础定制（内核 + 桌面）

| 任务 | 负责人 | 交付物 | 验收标准 |
|------|--------|--------|---------|
| Ubuntu 24.04 LTS 定制镜像 | 全栈工程师 | ISO 文件 | 可启动、可网络安装 |
| 桌面环境定制（主题/壁纸/图标） | UI/UX 工程师 | Cinnamon 主题包 | 品牌视觉统一 |
| 预装驱动包（显卡/网卡/蓝牙） | 系统工程师 | 驱动 .deb 列表 | 主流硬件自动识别 |
| 预装 Wine 7.x（最新版） | 系统工程师 | Wine 配置 | `winecfg` 可正常运行 |

**关键动作**：选 Cinnamon 而非 GNOME（低资源 + 可深度定制），减少 Phase 1 UI 工作量。

### Week 3–5：Wine 兼容层核心调优

| 任务 | 负责人 | 交付物 | 验收标准 |
|------|--------|--------|---------|
| Wine prefix 预设（win10/win11 兼容） | 系统工程师 | 预配置 prefix | 常见 .exe 双击直接运行 |
| DXVK / VKD3D 集成（DirectX 11/12） | 系统工程师 | 显卡加速 | 3D 应用帧率 ≥ 原生 70% |
| 字体渲染优化（微软雅黑/宋体嵌入） | UI 工程师 | 字体包 | 中文界面无乱码 |
| Wine 辅助脚本（wine-run.sh 一键启动） | 全栈工程师 | Shell 脚本 | `wine-run app.exe` 替代拖拽 |

**验收测试集**：
- 钉钉/飞书/微信（Windows 版）
- Microsoft Office（Word/Excel/PowerPoint）
- Photoshop 2023
- 腾讯会议
任选 5 款主流软件，覆盖办公、通讯、设计三类，Wine 运行成功率 ≥ 80% 为 Week 5 里程碑。

### Week 6–8：应用商店 + 安装体验

| 任务 | 负责人 | 交付物 | 验收标准 |

### Week 9–10：ISO 封装 + 测试

| 任务 | 负责人 | 交付物 | 验收标准 |
|------|--------|--------|---------|

### Week 11–12：内部 Alpha 发布 + 复盘

## 三、Phase 2 计划（Week 13–26）

**目标**：从"能用"到"好用"，建立可持续运营的应用生态。

### 3.1 Wine 应用认证商店

核心逻辑：Wine 运行 Windows 软件不是 100% 可靠的，不同版本、不同补丁状态表现差异极大。**认证 = 有人测试过、知道哪些版本能跑、有问题记录**。

**Phase 2 交付物**：

#### ① 开发者 SDK（降低 Wine 适配门槛）

```
Wine-Adapter-SDK:
  ├── wrapper.sh          # 封装 wine-run 逻辑
  ├── prefix-manager      # 预设 Wine prefix 管理
  ├── dependency-checker  # 自动检测所需依赖（.NET/VC++）
  ├── performance-tuner   # DXVK/DirectX 自动切换
  └── submit-portal       # 开发者提交认证申请
```

开发者通过 SDK 提交应用 → CI 自动跑兼容性测试 → 认证评级（Gold/Silver/Bronze）→ 上架商店。

#### ② 认证体系设计

| 认证等级 | 要求 | 商店标识 |
|---------|------|---------|
| Gold | 核心功能 100%，性能 ≥ 原生 90% | 🥇 金牌认证 |
| Silver | 核心功能 100%，性能 ≥ 原生 70% | 🥈 银牌认证 |
| Bronze | 核心功能可用，有已知 Bug | 🥉 铜牌认证 |
| Alpha | 部分功能可用 | 🧪 实验级 |

#### ③ 社区共建机制

- **用户提交问题**：商店内置"报告问题"按钮，自动收集 Wine 日志
- **志愿者适配组**：开源社区贡献者认领应用适配
- **积分激励**：适配贡献可兑换商店积分

### 3.2 Phase 2 周计划

| 阶段 | 周数 | 重点 |
|------|------|------|
| SDK 开发 | Week 13–16 | SDK 核心功能 + CI 流水线 |
| 认证流程设计 | Week 14–17 | 评级标准 + 审核机制 |
| 商店功能完善 | Week 16–20 | 搜索/评论/积分/支付 |
| 引入前 50 款认证应用 | Week 18–22 | 办公/开发/设计/游戏各方向 |
| Beta 发布 + 社区运营启动 | Week 23–26 | 公开测试 + 收集反馈 |

## 四、Phase 3 判断：Darling / macOS 兼容性

### 4.1 技术现状

| 维度 | 评估 |
|------|------|
| Darling 项目状态 | 2026 年仍在开发，仅支持极少量 macOS CLI 工具，无 GUI 支持 |
| macOS 应用生态 | 几乎全部重度依赖 Apple 私有框架（AppKit、SwiftUI、Metal） |
| Apple 法律风险 | macOS 授权明确禁止在非 Apple 硬件上运行（EULA §2.B） |
| 硬件依赖 | Apple Silicon / T2 芯片强绑定，无替代路径 |
| Wine/macOS 历史 | 2020 年 macOS 版 Wine（Winehq 6.0）已放弃维护 |

### 4.2 结论：**不建议**

**理由**：
1. **技术差距最大**：macOS 应用依赖的框架层比 Windows 更封闭、更私有，兼容性挑战是 Wine 的 3–5 倍
2. **法律红线**：Apple EULA 明确禁止虚拟化 macOS，强制非 Apple 硬件运行 macOS 应用存在侵权风险
3. **投入产出比最差**：即使花了 2 年适配主流 macOS 应用，用户基数也比 Windows 小得多（国内桌面市场 Windows 占 80%+）
4. **Darling 项目不成熟**：至今无 GUI 应用成功运行案例，不具备工程化基础

**明确结论**：**Phase 3 暂停 macOS 兼容性路线。**

**替代建议**：如果 Phase 1/2 验证成功，Phase 3 资源应投入：
- **Wine 深度优化**（性能提升、游戏支持、反作弊兼容性）
- **Android 子系统**（部分 APK 办公应用可移植，实操性更强）
- **Web 应用生态**（Electron/Flutter 应用天然跨平台）

  兼职：Product Owner（需求优先级）

  职责：
    - Ubuntu 定制（ISO 封装、内核配置）
    - Wine 核心调优（prefix、DLL、DXVK）
    - APT 仓库运维
    - CI/CD 流水线
  核心技术栈：Linux 内核 / Ubuntu / Wine / Shell scripting / Docker

前端 + 全栈工程师 × 1
  职责：
    - 桌面环境定制（Cinnamon 主题）
    - 图形化商店前端（GTK/Vala 或 Electron）
    - Wine 辅助脚本（wrapper/launcher）
    - 应用元数据管理
  核心技术栈：Vala 或 Electron / Python / SQLite / GTK

**3 人 MVP 的局限**：
- 驱动兼容性测试靠手动，无法系统化
- QA 依赖人工，无法做自动化回归测试
- 应用认证靠社区，无法保证质量

## 七、TOP3 风险 + 应对预案

### 风险 1：Wine 兼容率达不到预期（最核心风险）

**场景**：Phase 1 结束时，主流软件 Wine 兼容率低于 60%，大量应用无法使用。

**原因**：
- 某些软件重度依赖 Windows 特有 API（COM、ActiveX、.NET Framework）
- 企业软件（钉钉、企业微信）反逆向保护导致兼容层失效

**应对预案（分级）**：
| 兼容率区间 | 应对策略 |
|-----------|---------|
| ≥ 80% | 正常推进 Phase 2 |
| 60–79% | 聚焦高频应用专项适配（成立"钉钉适配小组"等） |
| 40–59% | 重新定义产品定位：不做全兼容，改为"Wine 应用精选发行版" |
| < 40% | 暂停，转向 Flutter/Tauri 跨平台运行时路线（轻量得多） |

**主动降低风险**：Week 1–2 先跑一遍 Phase 1 验收测试集（5 款软件），若 Wine 成功率 < 50%，立即开会对齐路线。

---

### 风险 2：团队技术天花板（Wine 调优人才稀缺）

**场景**：Wine 深度问题（Win32 API 翻译 Bug、性能瓶颈）卡住进度，没有人能解决。

**原因**：Wine 专家全球稀缺，国内更少；Wine 调优需要大量踩坑经验积累。

**应对预案**：
1. **Week 1 前**：联系 WineHQ 社区 / Proton（Steam）贡献者，建立技术顾问关系（远程兼职）
2. **备选方案**：将 Wine 调优模块外包给有经验的海外开发者（Upwork/Fiverr 验证过可行）
3. **技术储备**：订阅 Wine 邮件列表 + Proton 开发博客，提前获知已知 Bug 和 workaround

---

### 风险 3：法律风险（知识产权灰区）

**场景**：收到微软/Adobe 等公司的侵权警告信，或应用商店被迫下架某些应用。

**原因**：Wine 的法律地位是"干净 room 实现"，但"协助用户规避授权"可能触碰红线。

**应对预案**：
1. **明确边界**：项目定位为"基于开源 Wine 的 Linux 定制发行版"，不做任何逆向或补丁分发
2. **应用商店分级**：不主动收录需要破解/激活的软件，仅收录可通过官方试用版/开源软件
3. **法律顾问**：在发布公测版前，咨询一次软件法律师（2000–5000 元/次），明确边界
4. **域名/商标隔离**：确保项目名称不与 Windows/macOS 商标近似，降低品牌关联风险
